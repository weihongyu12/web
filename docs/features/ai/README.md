# AI 编程

:::warning
AI 领域发展迅速，本章内容具有时效性，部分信息可能随生态演进而滞后。
:::

## 1. 背景与演进

软件工程的写法正在被重新定义。从最初的行级代码补全，到对话即编辑的 AI 原生 IDE，再到以终端为载体的自主编程 Agent，AI 编程工具的形态正从"辅助"走向"主导"。伴随工具演进的，是模型能力、协议标准、项目上下文规范的整体升级。

当前 AI 编程生态可归纳为三层结构：

| 层级 | 内容 | 决定的问题 |
| --- | --- | --- |
| 模型层 | Claude Sonnet、GPT Codex、GLM 5.2、Kimi K3 等 | 能不能想到 |
| 工具层 | Cursor、Claude Code、Codex、Trae CN 等 | 能不能做到 |
| 协议与约定层 | MCP、AGENTS.md、llms.txt、Skills | 是否可控、可复用、可协作 |

三层共同决定一次 AI 编程体验的上限。理解三层结构，比单纯追逐某一工具或模型更重要。

## 2. 主流工具

当前 AI 编程工具大致分为三类形态：嵌入式 IDE、AI 原生 IDE、终端 Agent。

### 2.1 Cursor

Anysphere 推出的 AI 原生 IDE，基于 VS Code 分叉构建。将 AI 能力深度嵌入编辑器内核，提供 Tab 智能补全、Cmd+K 行内编辑、Composer 多文件改动、Agent 模式自主执行等能力。

优势在于交互体验成熟、上下文管理精细（通过 `@file`、`@codebase`、`@docs` 等符号精确控制上下文），适合追求"边写边问"流畅体验的场景。

### 2.2 Claude Code

Anthropic 官方推出的命令行 AI 编程工具。与 IDE 解耦，直接运行在终端中，能够读取项目文件、执行命令、运行测试、提交代码，以 Agent 形式自主完成多步骤任务。

强调"少打扰、多做事"，适合长流程的重构、迁移、批量改动等场景，也可与任意编辑器组合使用。

### 2.3 Codex

OpenAI 推出的编程 Agent 工具，以 CLI 为核心载体，结合云端的 Codex 模型执行任务。支持在仓库中并行处理多个任务，强调"任务委派"模式——描述意图，Codex 在隔离环境中规划并执行改动，再返回结果供审查。

提供 IDE 插件，但核心思路仍是云端 Agent。

### 2.4 Trae CN

字节跳动推出的 AI 原生 IDE 国内版，面向中文开发者。在 Cursor 式的对话编辑体验基础上，接入国产模型（如 GLM、Doubao 等），并对中文语境、国内开发工作流做了适配。

对于受网络与合规限制、希望使用国产模型栈的团队，提供了一条可行路径。

### 2.5 工具对比

| 工具 | 形态 | 默认模型 | 核心场景 |
| --- | --- | --- | --- |
| Cursor | AI 原生 IDE | 多模型可选 | 对话式编辑、精细上下文控制 |
| Claude Code | 终端 Agent | Claude Sonnet | 长流程自主任务、可搭配任意编辑器 |
| Codex | 终端 Agent + 云端 | GPT Codex | 任务委派、并行处理 |
| Trae CN | AI 原生 IDE | GLM / Doubao 等 | 国产模型栈、中文语境适配 |

## 3. 核心模型

工具的能力上限，最终由背后的模型决定。当前在编程任务上表现突出的模型主要有以下几类。

### 3.1 Claude Sonnet

Anthropic 的 Claude Sonnet 系列定位为"性能与成本平衡"的主力模型。在编程任务上长期处于第一梯队，尤其在长上下文理解、代码重构、Agent 多步推理方面表现稳定。Claude Code 默认即基于 Claude Sonnet 系列模型。

### 3.2 GPT Codex

OpenAI 面向软件工程优化的模型，专为 Agent 化的编程任务训练。在理解大型代码库、规划跨文件改动、执行测试与验证方面具有较强能力，是 Codex 工具的默认模型。

### 3.3 GLM 5.2

智谱 AI 推出的编程向模型，在中文代码场景、国产化技术栈适配上具有优势。常作为 Trae CN 等国产工具的后端模型之一，提供符合国内合规要求的编程能力。

### 3.4 Kimi K3

月之暗面推出的模型，以超长上下文窗口见长，适合处理超大代码库、长文档分析等需要海量上下文的场景。在需要一次性"吞下"整个仓库或长篇技术文档的任务中具有独特价值。

### 3.5 模型选型参考

| 模型 | 强项 | 典型场景 |
| --- | --- | --- |
| Claude Sonnet | 长上下文、Agent 推理 | 重构、迁移、多步任务 |
| GPT Codex | 大仓库理解、跨文件规划 | 任务委派、批量改动 |
| GLM 5.2 | 中文场景、国产适配 | 国内合规项目 |
| Kimi K3 | 超长上下文 | 超大仓库、长文档分析 |

## 4. AGENT 智能体

AGENT（智能体）是当前 AI 编程的核心范式。与传统"单轮问答"不同，Agent 能够：

- **自主规划**：将高层目标拆解为可执行步骤
- **调用工具**：读写文件、执行命令、调用 API、访问网络
- **观察反馈**：根据执行结果（报错、测试输出）调整后续行动
- **循环迭代**：在多次尝试中逐步逼近目标

Agent 的价值在于把开发者从"逐行写代码"解放为"描述意图并审查结果"。Claude Code、Codex 即是典型的 Agent 形态工具。

Agent 也带来新的挑战：可控性、安全性、成本控制，以及对项目上下文的依赖。后续的 MCP、AGENTS.md、Skills 等约定，本质上都是在回应这些挑战。

## 5. MCP Server

MCP（Model Context Protocol）是 Anthropic 于 2024 年底提出并开源的协议，用于标准化 AI 模型与外部数据源、工具之间的连接方式。

### 5.1 架构

MCP 采用 Client–Server 架构：

- **MCP Server**：暴露特定能力（如读数据库、查文档、操作飞书、调浏览器）给 AI
- **MCP Client**：内嵌在 AI 工具中（Claude Code、Cursor、Trae 等均支持），消费 Server 提供的能力

### 5.2 价值

MCP 的意义在于**解耦**：

- 工具厂商不必为每个外部系统单独写集成
- 外部系统也不必为每个 AI 工具做适配
- 任何符合 MCP 协议的 Server，都能被任何支持 MCP 的 Client 调用

这极大降低了生态碎片化，让 AI Agent 真正具备"连接万物的手"。

### 5.3 典型场景

- 通过 MCP Server 让 AI 读写数据库
- 操作云服务（OSS、CDN、容器）
- 检索企业知识库
- 控制浏览器执行 E2E 测试
- 对接协同工具（飞书、Jira、Git）

## 6. 项目上下文标准化

Agent 要在具体项目中高效工作，前提是"看懂项目"。围绕这一需求，社区演化出几项约定。

### 6.1 AGENTS.md

`AGENTS.md` 是一项开放标准，约定在项目根目录放置一份 Markdown 文件，向 AI Agent 提供项目级的指令与上下文，例如：

- 项目结构与目录约定
- 编码规范、命名规则
- 构建、测试、部署命令
- 不应触碰的敏感文件
- 特定的技术决策与原因

`AGENTS.md` 类似于给新成员的"入职手册"，让 Agent 在动手前先理解项目的"规矩"。与 Claude Code 的 `CLAUDE.md`、Cursor 的 `.cursorrules` 思路一致，但追求跨工具通用。

### 6.2 llms.txt

`llms.txt` 借鉴 `robots.txt` 的思路，是面向大语言模型的网站信息标准（由 llmstxt.org 推动）。网站在根路径放置 `llms.txt`，以 Markdown 格式提供：

- 站点概览与核心价值
- 关键页面链接
- 文档摘要
- 对 LLM 友好的内容索引

目标是让 LLM 在被问及某网站/产品时，能快速获取权威、结构化的信息，而非依赖训练数据中可能过时的片段。对文档站点、API 平台、开源项目尤其有用。

### 6.3 Skills

Skills 是"可复用能力封装"的统称，不同工具实现略有差异，核心思路一致：将一类常见任务（如"生成 REST 接口""发飞书消息""跑测试并修复"）封装为带描述、参数、执行逻辑的技能单元，供 Agent 按需调用。

Skills 的价值在于：

- **复用**：把团队沉淀的工作流固化为可调用的能力
- **可控**：明确定义 Agent 能做什么、不能做什么
- **组合**：多个 Skill 可被 Agent 串联完成复杂任务

与 MCP Server 形成互补：MCP 偏向"连接外部系统"，Skills 偏向"封装内部工作流"。

### 6.4 约定对比

| 约定 | 作用范围 | 核心目标 |
| --- | --- | --- |
| AGENTS.md | 项目内 | 让 Agent 理解项目规矩 |
| llms.txt | 网站根路径 | 让 LLM 获取站点权威信息 |
| Skills | 工具/团队级 | 封装可复用工作流 |
| MCP Server | 跨系统 | 标准化连接外部能力 |

## 7. 实践建议

### 7.1 工具与模型组合

没有"唯一正确"的工具选型，组合取决于项目特征与团队约束：

- 受合规限制的国内项目：Trae CN + GLM 5.2 / Doubao
- 长流程重构与迁移：Claude Code + Claude Sonnet
- 对话式日常开发：Cursor + 多模型按需切换
- 超大代码库一次性分析：Kimi K3 长上下文能力

### 7.2 项目上下文建设

无论选择哪款工具，都应重视项目上下文建设：

1. 维护 `AGENTS.md`（或对应工具的等价文件），明确项目规矩
2. 对外文档站点补充 `llms.txt`，提升 LLM 可读性
3. 将高频工作流封装为 Skills，沉淀团队经验
4. 通过 MCP Server 接入外部系统，扩展 Agent 能力边界

### 7.3 可控性与成本

Agent 模式下需关注：

- **可控性**：明确 Agent 的权限边界（可读写哪些路径、可执行哪些命令）
- **安全性**：避免 Agent 触碰密钥、生产环境、敏感数据
- **成本控制**：长流程任务消耗 token 较多，需结合预算与任务价值评估

## 8. 结语

AI 编程的竞争力，不在于会用某款工具，而在于能否围绕项目特征，组合模型、工具、协议与约定，构建出可控、高效、可演进的 AI 编程工作流。模型决定"能不能想到"，工具决定"能不能做到"，协议与约定决定"做得是否可控、可复用、可协作"——三层协同，才是 AI 编程的完整图景。
